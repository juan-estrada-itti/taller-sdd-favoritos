# Design: SDD Health Check · MVP para medir adopción del way of work en brownfields

Generated by /office-hours on 2026-04-24
Branch: main
Repo: taller-sdd-favoritos (workspace del Taller 2 SDD, pero el MVP apunta a academy/ittilab)
Status: DRAFT
Mode: Startup (intrapreneurship)

## Problem Statement

Juan, como lead de la plataforma de skills de tech emergentes en itti-digital, propone un MVP que automatice la cadena PRD → RFC → ADR → Historias → Plan para proyectos brownfield de la organización. La hipótesis inicial era que el cuello de botella es el **costo de generar artefactos**. Durante la sesión esa hipótesis se cayó: el way of work manual ya existe y está documentado (8 skills desplegadas, caso AppSec probado end-to-end), pero los builders de academy e ittilab **no lo están usando en la práctica**. El problema real no es velocidad de generación sino **adopción y percepción de valor**.

El MVP reenfocado: dado que nadie usa el way of work, el primer paso no es automatizar su generación sino **diagnosticar qué tan lejos está cada proyecto brownfield del estado deseado** y entregarle esa visibilidad al tech lead de forma pasiva, sin pedirle que cambie su workflow.

## Demand Evidence

Evidencia fuerte de demanda: **ninguna todavía**. Juan explicitó que la motivación es "hipótesis del lead" — no tiene una persona específica fuera de su equipo de 5 expertos que haya pedido el MVP. Cuando se le preguntó por una persona concreta que lo adoptaría si existiera, pudo nombrarla (tech lead de academy/ittilab) pero reconoció que **no sabe por qué esa persona no está usando el way of work manual hoy**. Esto es el dato más importante de la sesión y el que define la forma del MVP: antes de construir cualquier cosa, hay que validar si la demanda existe.

La "demanda negativa" sí es observable: los artefactos SDD en academy/ittilab están en estado de letra muerta ("ni siquiera lo intentan" fue la respuesta literal). Eso sugiere que el problema percibido por el usuario NO es el que Juan asumía.

## Status Quo

Hoy, en academy e ittilab:
- El way of work existe documentado (skills en `~/.claude/skills/` + caso de referencia AppSec Q1 2026).
- En la práctica, los equipos codean como antes — los artefactos SDD no se generan, o se generan una vez y quedan desactualizados.
- El equipo de 5 expertos de Juan es el único que usa el pipeline activamente.
- Los ~15 builders de la org: no adoptan.

## Target User & Narrowest Wedge

**Usuario target:** tech lead de un proyecto brownfield de itti (academy o ittilab), no miembro del equipo de 5 expertos.

**Wedge elegido:** health check pasivo del proyecto. El MVP **no genera artefactos**. Solo escanea los repos del proyecto y produce un reporte que dice "te faltan estos ADRs, este RFC está desactualizado, estas historias no tienen plan". El lead no hace nada distinto — el reporte le llega.

Este wedge es el único que:
- No compite con el workflow actual del lead
- Falla barato (si no lo mira en 2 semanas = demanda cero, matás el proyecto)
- Revela la demanda real antes de invertir en generación

## Constraints

- El MVP se prueba en UN solo proyecto (academy o ittilab), no ambos
- Un proyecto puede abarcar N repos (input del MVP = manifiesto yaml con lista de repos, no URL de repo)
- El lead no corre nada, no instala nada, no entra a ningún sitio nuevo
- Métrica de validación = comportamiento (¿abre el reporte? ¿lo comenta? ¿arregla algo?), no opinión
- Primer incremento = solo diagnóstico. Generación de artefactos viene después si y solo si el lead lo pide

## Premises

1. El problema real es falta de diagnóstico, no falta de velocidad de generación. **Aceptada.**
2. El MVP se prueba en UN solo proyecto (1 o más repos del mismo proyecto) — no multi-tenant cross-proyecto. **Aceptada tras revisión** (la versión original decía "1 repo" y Juan la desafió correctamente).
3. Métrica de validación es de comportamiento, no opinión. **Aceptada.**
4. El MVP NO genera artefactos. Solo diagnostica. Generación es el siguiente incremento si hay pedido real. **Aceptada.**
5. El equipo de 5 expertos NO es el primer cliente. El target son los ~15 builders que hoy no adoptan. **Aceptada.**

## Approaches Considered

### Approach A · CLI local + markdown report
Binario TS que el lead corre manual. Lee manifiesto, clona repos, escanea árbol de artefactos, genera markdown. Cero infra. Efforts: humano 2-3 días / CC ~2h. Risk: Low. Problema: el lead tiene que acordarse de correrlo, y el default en esta org es no acordarse de correr nada.

### Approach B · GitHub App + dashboard web
App instalable en la org, dashboard Next.js, alertas Slack. Effort: humano 3-4 semanas / CC ~5 días. Risk: High. Problema: requiere infra antes de validar demanda. Si el lead no mira el dashboard, perdiste semanas.

### Approach C · GitHub Action que abre un issue semanal (elegida)
Cron semanal que escanea los N repos del proyecto y abre/actualiza un issue en un repo meta con el reporte. El lead recibe notif de GitHub como cualquier otra. Effort: humano 3-4 días / CC ~3h. Risk: Low-Med. Ventajas: push al lead (no pull), usa GitHub como infra, la métrica de demanda se auto-genera en el tracking del issue.

## Recommended Approach

**Approach C · GitHub Action + issue semanal.**

Razón: es el único approach que cumple literal el criterio del wedge — "entregar valor sin que el usuario haga nada distinto". El issue queda en un lugar que el lead ya mira. Los comentarios/assignees/close del issue son la métrica de demanda gratis. Si en 2 semanas el issue sigue sin tocar, la hipótesis se cae barata y sin infra que desmontar.

## Open Questions

- **¿Juan tiene permisos de admin en los repos de academy/ittilab** para configurar la GitHub Action? Si no, el fallback es Approach A con un tech lead que colabore como cómplice.
- **¿Qué define "estado esperado" en el reporte?** El contenido del health check depende de tener un checklist claro: qué artefacto debe existir en qué carpeta para cada proyecto. Ese checklist vive en `CLAUDE.md` del repo + las skills de `tech_emergentes_skills`. Hay que formalizarlo antes de escanear.
- **¿Quién recibe la notif del issue?** Si solo Juan, el test de demanda falla porque Juan está sesgado. Taggear al tech lead del proyecto.
- **¿Qué pasa si el lead abre el issue pero no entiende el reporte?** Segundo tipo de falla. Cubrir con un formato de reporte simple desde día 1.

## Success Criteria

En las **2 semanas** posteriores al primer issue abierto automáticamente:

- **Demanda validada (continuar):** el lead tocó el issue (commenteó, assignó, cerró con razón) O preguntó a Juan/el equipo por alguno de los gaps listados.
- **Demanda falsificada (matar):** el issue queda abierto, sin tocar, no referenciado por nadie.
- **Señal ambigua (iterar):** el lead lo leyó pero no actuó. Entrevistarlo para entender si es claridad del reporte o falta de incentivo.

## Distribution Plan

El MVP se despliega como una GitHub Action en un repo meta del proyecto (ej: `academy-meta` o el repo principal de academy). Configuración:
- `.github/workflows/sdd-health.yml` con cron semanal (ej: lunes 9am UYT)
- Repo meta tiene permisos de read en los repos del proyecto (ya existentes dentro de la org)
- El script TS vive en `.github/scripts/` del repo meta (inline, no empaquetado) o se instala desde un paquete privado de npm publicado por el equipo de Juan
- No hay CI/CD externo — la Action ES el runtime. Cero hosting.

Para el segundo proyecto (si sobrevive al primero), se copia la misma Action + el manifiesto apuntando a los repos de ittilab. Cuando haya 2-3 proyectos usándolo, evaluar empaquetar como Action reusable publicada en el marketplace interno.

## Dependencies

- Acceso admin a un repo meta en la org de academy (o ittilab)
- Formalizar el checklist de "estado esperado" de un proyecto SDD en itti (puede derivarse de `CLAUDE.md` + pipeline-greenfield.md)
- Tech lead cómplice para el piloto: alguien de academy o ittilab que sepa que el issue va a aparecer y esté dispuesto a dar feedback honesto (no para darle el gusto a Juan — para decir "no sirvió")

## The Assignment

**Antes de escribir una línea de código**: sentate 30 minutos con el tech lead de academy o ittilab (la persona que nombraste) y preguntale una sola cosa — *"¿Por qué no estás usando el way of work que el equipo desplegó?"*. No le pitches el MVP. No le cuentes que estás pensando en automatizar nada. Solo escuchá.

Tres cosas específicas que querés salir sabiendo:
1. ¿El problema real es que no confía en el output, que no tiene tiempo de aprender las skills, que no ve el valor, o algo que no está en esa lista?
2. ¿Un reporte que diga "te falta X, Y, Z" lo movería o lo frustraría?
3. ¿Dónde querría recibirlo — GitHub issue, Slack, email, otro lado?

Si la respuesta a #2 es "me frustraría", el MVP que acabamos de diseñar es basura y hay que volver a Phase 2. Es más barato enterarte antes de construir.

Volvé con las 3 respuestas y ajustamos el approach. Entonces arrancamos código.

## What I noticed about how you think

- Cuando te tiré que "hipótesis del lead" es la respuesta más peligrosa en intrapreneurship, no te pusiste defensivo — firmaste la respuesta como tal. Esa honestidad es rara. La gente que empieza proyectos internos suele inflar la demanda antes de empezar; vos no lo hiciste.
- Cuando propuse la premisa "un solo repo", me corregiste con "¿y si es un proyecto de varios repos?". Ese push-back no fue por cabezón — fue porque conocés tu org mejor que yo y te diste cuenta que mi modelo estaba mal. Tomé nota y reescribí la premisa. Lo que me dijiste fue más valioso que lo que yo propuse.
- Cuando no entendiste las 3 alternativas técnicas, dijiste "no entiendo" en lugar de fingir que sí. Eso es lo que separa a la gente que shippea producto real de la que construye torres técnicas que nadie usa. La señal no es "sé las palabras de moda", la señal es "exijo que me lo expliquen hasta que me cierra".
- Estás diseñando infraestructura de proceso para 20 personas cuando muchos leads de tu tamaño solo compran herramientas off-the-shelf y rezan. Eso dice algo sobre cómo ves tu rol: no como administrador del status quo, sino como constructor.

## Evolución del entendimiento · 2026-04-24 (addendum)

Después de escribir este discovery, Juan arrancó `/create-prd` y durante la conversación identificó que el problema real no era "detectar el gap" (la tesis del MVP health check) sino **"no sé qué contexto meterle a las skills SDD para que los RFCs y ADRs salgan bien en brownfields"**. Esa frase textual lo llevó a un pivot hacia un **MVP de "Context Packager"** que inferiría automáticamente 5 archivos clave (CLAUDE.md, journeys, patterns, ADRs retrospectivos, api-contract) desde el código existente.

El pivot se documentó como PRD v0.2 (archivado · ver `docs/01-prd/prd.md` con header `ARCHIVED`).

### Validación adversarial del PRD v0.2 · resultado 4/10

El PRD v2 se sometió a un review adversarial independiente. Findings críticos:

1. **Contradicción interna**: el discovery firmó "el MVP no genera artefactos, solo diagnostica" (premisa #4). El PRD v2 generaba 5 archivos — cambio silencioso de scope sin renegociar la premisa.
2. **Evidencia N=1**: toda la fuerza del pivot descansaba en el caso AppSec Q1 2026, tratado como ley universal cuando es una anécdota.
3. **Métrica no falsable**: A/B blind review con N=2, single rater, rúbrica sin operacionalizar, baseline pendiente.
4. **Scope oculto**: "inferir journeys de controllers" y "extraer schemas de 3 sistemas de tipos" son proyectos, no features, escritos como 1 línea.
5. **Premisa más frágil**: que la inferencia automática produzca packs de calidad comparable a los que el equipo hizo a mano en AppSec — sin evidencia ni en un repo piloto.

Score: **4/10**. Veredicto: volver al discovery antes de gastar más tiempo en artefactos posteriores del pipeline.

### Qué sigue (reafirmación)

La asignación original de este discovery — **"30 minutos con el tech lead de academy o ittilab para preguntar por qué no está usando el way of work"** — no se hizo. El PRD v2 fracasó en la validación adversarial en parte porque se saltó esa entrevista. El giro hacia "context packager" es una hipótesis mejor que la original, pero sigue siendo hipótesis mientras no haya N>0 usuarios entrevistados.

**Hasta que la entrevista se haga, el pipeline se queda en fase 1 (discovery). No avanzar a PRD.**

Si tras la entrevista el problema confirmado es "el contexto tácito del brownfield bloquea la adopción del pipeline", un POC mínimo (inferir SOLO un archivo, ej: CLAUDE.md para academy) es la primera validación técnica — antes de escribir otro PRD.

### Meta-learning para el way of work

Este episodio documenta un patrón aplicable a todos los brownfields de itti:
- Saltearse la entrevista de discovery por ir rápido al PRD produce PRDs que fallan validación adversarial
- El pipeline SDD es robusto solo si cada fase tiene el input validado de la anterior
- V2 del way of work global ("validar cada paso contra el PRD de negocio") se aplica también al discovery vs PRD, no solo del PRD hacia adelante
